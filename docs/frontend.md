# Frontend

The React app (`frontend/`, Vite + TypeScript, CSS Modules) is the face of Model X-Ray. It talks only to the HTTP API (`docs/api.md`). Issues: #74, #128.

## Running it

```
scripts/dev.sh
```

One command: installs the missing dependencies with bun (npm when bun is not on PATH), starts the API on `http://localhost:8000` and the app on `http://localhost:5173`, prints both URLs and which runner it uses, and stops both on Ctrl+C. Running them separately still works: `scripts/serve.sh`, then `cd frontend && bun install` (or `npm --prefix frontend install`) and `bun run dev`. A second dev server — two checkouts, or one started while `5173` is busy — lands on `5174` and still gets its data, because the API accepts any `localhost` port; the demo entry only disappears when the API itself is unreachable, which the landing says in its own words. `VITE_API_URL` points the app at another API, e.g. the deployed one. Tests: `cd frontend && bun run test` or `npm --prefix frontend test`; production build: `cd frontend && bun run build`. Layout checks that jsdom cannot make — a `before -> after` pair staying on one line, the sheet fitting without horizontal scroll — are screenshots: `scripts/screenshots.sh` renders the approved story through headless Chromium at 1280x800 and 1440x900 (the narrowest window the demo must survive, and a common laptop) into `/tmp/model-x-ray-screenshots`, and the invariant is that no cell grows a second line and no scrollbar appears at either width.

## Design system

Three layers, no legacy stylesheet:

| Layer | File | Holds |
|---|---|---|
| Tokens | `src/styles/tokens.css` | Every color as a CSS custom property, the type scale including the `--display` serif (Newsreader) for headlines, radii, motion tokens (`--dur*`, `--ease`), and the glow theme as alternate token values only (`[data-theme="glow"][data-variant=…]`) |
| Base | `src/styles/base.css` | Reset, `body` defaults, focus ring, the `.mono` and `.visually-hidden` utilities, the shared `fade-up` / `grow-x` / `scan` / `ring-pulse` keyframes, and a global `prefers-reduced-motion` kill switch |
| Components | `src/components/*.module.css` | Everything else, scoped to one component. A component never styles another component's DOM; the two exceptions are `:global([data-theme="glow"])` decoration rules that live in `Hero.module.css` and the forced-light `SheetGrid` island via its `light` prop |

Conventions: sizes in `rem` (hairline `1px` borders and focus outlines excepted), colors only through tokens, motion only through `--dur*`/`--ease` transitions and the shared keyframes.

The visual language is strict 70/20/10: about 70% plain white, 20% near-black ink for structure and text, 10% dark green (`--accent: #0d5c33`) as the only chromatic voice; red/amber appear only as semantic evidence colors. There is exactly one typeface — Inter — for everything (single font token `--sans`). The whole app fills the viewport with no page scrolling: `body` is `100dvh` with `overflow: hidden`, the shell is a CSS Grid (`auto minmax(0,1fr) auto`) capped at `100rem` and centered, the stage sizes with `minmax(0, 1fr)` so large models scroll inside the sheet area instead of the page. The workspace is a two-column flex row — the step column at `16rem`, then the sheet — and it stays two columns down to `60rem` of window width (below that the column stacks above the sheet and the page scrolls) and keeps every pipeline step visible down to `52rem` of window height (below that the column's heading drops and the rows tighten; the sheet itself has scrolled internally since long before). The sheet asks for at least `96px + 64px per period column` so a narrow window shrinks the columns instead of cutting them off. The landing is a two-column grid: on the left, the headline block ("Every formula, checked. / Under the X-Ray.") with a staggered rise reveal, a rotating "Ask" line that cycles three sample questions in sync with the demo cycle, the CTAs and an animated four-step timeline (Scan → Anomaly → Trace → Fix & verify) whose dots and titles light up in sync with the demo; on the right, the interactable example sheet as the largest element with the full choreography — a green scan line sweeps while rows flash one by one under it, H6 flags red, the provenance cells H4/H5 flash green during the trace, H8 gets the impact outline, then the fix swaps H6 to 97.2 and EBITDA to 44.7 under a floating "EBITDA 44.7 ✓" chip. All of it shares one 11-second CSS cycle (`--cycle`) so every element stays in phase; the loop clears at ~96% and restarts. There is no black or dark block on the landing. A dev-only `?demo-t=` query param shifts the whole cycle (`--demo-shift`) so any phase can be pinned for screenshots; below ~840px window height the landing scrolls internally instead of cropping.

`preview.html` + `src/preview.tsx` render every workspace state (the stage mid-run, paused and approved, the facts bar, the step column, primitives) on one dev-only page — never part of the production build. It is the fastest way to eyeball a style change: open `http://localhost:5173/preview.html` and screenshot.

The workspace is one stage in two columns: the step column and the sheet. The step column (`StepRail`) lists the eight pipeline steps — one line each, plus what the step found — and the sheet with its wiring and scan line fills the rest; the caption bar (`auto`) and the footer close the page. The sheet sizes to the sheet window and the stage scrolls internally when a model has more rows than fit; nothing else scrolls and there is no page scrollbar. The column and the sheet's frame stay on screen for the whole run: before the sheet window arrives — while the locator is still reading — the stage shows `SheetSkeleton`, the same spreadsheet chrome with placeholder rows, and a line saying what is being waited for (`Scanning the model — every formula, read in a copy`). A run that has not reached a cell yet therefore still shows the model and the eight steps instead of an empty page, and a refused `GET .../sheet` says so instead of leaving the stage blank. The previous report/tabs/side-rail workspace and its components were removed: the same facts live on the sheet (marks), in the step column and caption (target, checks, verdict) and in the `Why?` card (narrative).

Shared primitives in `src/components/`: `Button` (variants `primary`/`secondary`/`ghost`/`danger`; renders a `<button>`, a `<label>` with `htmlFor`, or an `<a>` with `href`), `Chip` (tones `neutral`/`green`/`red`/`amber`/`blue`, optional `pulse`), `Spinner`, `Alert` (red dot + `role="alert"` text, no box).

Performance: no new dependencies; the grid, report, detail tabs, progress and the decision panels are wrapped in `React.memo`, and `App` passes stable callbacks (`useCallback`) plus a `useMemo`-ised `Marks` object so streaming `step` events do not re-render them.

## Screen flow

1. **Home.** "Your Excel models under the X-Ray." with two actions: Upload your model (picks an `.xlsx`, uploads it with `POST /spreadsheets` and starts the check at once) and See it in action (starts a live check of the demo model from `GET /spreadsheets`; no recorded video). Both call `POST /investigations/stream` without a question: the agent decides where to look. Below: "Go beyond the numbers. See the logic." with the four steps as hairline-separated columns that reveal themselves on scroll. The example sheet on the right is the landing illustration.
2. **The stage (live).** There are no story sections: the field is the sheet, and the investigation is drawn on it. The server streams a `view` snapshot after **every** pipeline node (`tests/test_api_progress.py`).
   - **Step column (`StepRail`).** The eight steps of the pipeline, in order, one line each: "Opened the model", "Read the layout", "Found the cell", "Traced the inputs", "Found the root cause", "Tested the fix in a copy", "Checked the fix", "Wrote the explanation". `src/steps.ts` turns the view and the streamed steps into rows: a step that has not run yet shows what it will do ("What moved, and by how much"), a step that ran shows what it found (`Revenue +11.5 · COGS +189.5`, `P&L!G5 =G4*Assumptions!$C$5 → =-G4*Assumptions!$C$5`, `3 of 3 checks passed · proof passed`), and the step that is running now pulses. A step counts as run when its `step` event arrived **or** the view already carries its result, so a resumed run — which only re-tests, re-checks and re-writes the explanation — never restarts the column at step one,; steps outside the pipeline ("Saving a new version") are appended at the end. A step only counts as run on a *complete* result: mid-run the `test` node streams a verification that carries just the sandbox numbers (`before`, `after`) and the `verify` node merges the checks into it later, so "Checked the fix" stays the running step until the checks are there — reading the count off that half-filled verification is what used to throw and blank the page. The dot column is a rail that fills green from the top as the run advances; a detail longer than three lines is clamped and carries the full text in its tooltip.
   - **Sheet.** `Stage` centers the sheet window from `GET /investigations/{id}/sheet` and overlays an SVG layer. Marks: the target cell tinted, the suspect ringed red (pulsing while open), traced cells tinted green, and the tested fix shown in place as `value → corrected` with the corrected number in green.
   - **Wiring.** Every edge of the causal tree is drawn as an Excel-style trace: a dot on the source cell's border, a right-angle rail in the right margin (never over numbers), and an arrowhead on the total's border. Inputs into the same cell get their own lane and arrowhead. A rail turns red when its source is the confirmed suspect. The key sits in the caption bar: `•──▶ contributes`. Each arrow that reaches the questioned cell carries a callout chip next to its arrowhead with what the run found on that edge — the row, its contribution (`COGS +189.5`) and either the diagnosis in the run's own words (`sign inconsistency`, red, with the full claim on hover) or the share of the movement it explains (`6% of the move`); chips from the same cell stack downward when they would collide, and the broken edge's chip keeps the target row. When the questioned cell is a ratio (a margin, a growth rate, from the model map's `ratio` kind) the chips keep the driver's own change and drop the share of the move, which is meaningless when numerator and denominator move in opposite directions, and the target reads as a percentage (`105.0% → 120.0%`). Deeper edges of the tree are drawn but not annotated, so the sheet keeps one readable callout per cause. A chip never widens the stage: its left edge is clamped to the sheet's right edge plus the `5rem` gutter, so a total in the last column pushes its callout back over the sheet instead of clipping it or adding a scrollbar.
   - **Caption bar (`FactsBar`).** The target in one line (`Gross profit 2025A 84.7 → 285.8`), the cell the locator chose (`Chosen among 3 candidates: P&L!G6, Summary!G6, P&L!F6` when the question matched several, a quiet `Chosen: P&L!G6` when the code found one, with the locator's reason behind a `why?` toggle), the wire key, the three deterministic checks as dots, the verdict in two words ("Proof passed"), and `Why?`, which opens the narrative in a floating card over the sheet. Clicking an `ev-N` citation flashes the cell it refers to.
   - **Your call.** When the view is `needs_review`, the bar grows a decision row: reason (optional), "Never flag again", Approve fix / Edit fix (formula field, then Test my fix) / Reject. Once decided: "Fix applied to a new copy" with the `GET /investigations/{id}/corrected` link, or "Closed without changes".
   - **Receipts.** The footer carries the run's scale: `11 Nemotron calls · 27k tokens`.
3. **Stopped states.** Errors from the API or the stream appear as one short sentence in an alert. The case view is a flex column (topbar, alert, stage, caption, footer): the alert takes the height it needs, the sheet keeps the rest, and nothing collapses or leaves a gap. A refused input — an edited fix the server will not accept, e.g. a formula that cannot be calculated — keeps the sheet, the checks and the whole decision row on screen with the reason field as typed, and the chip goes back to "Review needed" so the reviewer can correct it and press Test my fix again. Because the stream hands the stage partial views by design, an error thrown while drawing one of them would otherwise unmount the whole page and leave the reviewer on a blank white screen; `Boundary` wraps the rail, the stage, the pause and the caption bar and replaces whichever of them threw with one short line and a "Start another check" button, so the worst case in a live demo is a readable message, never a white page.

The API ships everything the stage needs in one `InvestigationView`: `PUBLIC_FIELDS` includes `model_map`, `known_overrides`, `past_findings`, `contributions`, `target_choice`, `tool_call_counts`, `node_log`, `attempts` and `human_decision`, and each view carries `check_labels` (the human sentences for the deterministic checks).

## Recorded demo runs

The dev stories (`?story=starting`, `?story=workspace`, `?story=running`, `?story=done`) replay real investigations instead of hand-written fixtures: `starting` is a run whose first pass is still going (no view, no sheet, the first two steps done), the other three are a paused run, a mid-run snapshot and an approved run. `tools/export_demo_run.py` reads a paused run and an approved run from a live API and writes `src/test/recorded/{review,done,sheet}.json`; `fakeApi.ts` casts them to `InvestigationView` / `SheetWindow` and derives the running, starting and tested variants (the last one is the mid-run shape where the sandbox test has run and the checks have not). Re-record after any change to prompts, diagnosis or the sheet window so the demo keeps showing what the product actually produces. `?static` (dev only) pins the sheet wiring at its finished state so headless screenshots do not race the dash animation.

## Accessibility

Every control has a visible label; sections are named regions; the pause is a `fieldset` with its question as the legend; progress updates are announced (`aria-live`); errors use `role="alert"`; focus outlines are visible; all animation stops under `prefers-reduced-motion` (a global rule in `base.css`, plus `StepRail`'s reveal, whose staggered `animation-delay` would otherwise hold the last steps transparent).

## Tests

`src/test/app.test.tsx` drives the whole page through a fake API that streams real event shapes (`src/test/fakeApi.ts`), the way a user would: by labels, buttons and visible text. It covers a full investigation with approval and download, an intentional rejection, editing the fix, a failure message, what the step column says for every step of a finished run, how it lights up while the run is still going, that approving a fix does not restart the column, what each arrow into the questioned cell is annotated with (the contribution, the diagnosis of the broken edge, the share for the others, and nothing on the deeper edges), and the first pass that has not produced a sheet yet, which must keep the model's frame and the eight steps on screen — plus the mid-run shape that used to blank the whole page (the fix tested, its checks not in yet: the sheet, the chip on the fixed cell, the step column and the caption bar must all stay up, with "Checked the fix" still the running step). `src/test/crash.test.tsx` mocks the stage to throw and checks that the reviewer gets a readable message and a way back to the home page instead of a white screen. Because it queries by role and text, it pins the information architecture while the visual layer changes freely.
